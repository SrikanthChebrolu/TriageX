# Requirement 02 — Incident Triage & Prioritization

## Overview

Build a REST endpoint that accepts a new incident description and returns a triage
recommendation. The recommendation includes:

- A **priority score** (0–100) computed from similarity to past incidents, severity,
  number of affected services, and time of day.
- **Investigation steps** — a ranked, ordered checklist generated by pattern-matching
  against known common web-application error signatures.
- **Similar past incidents** retrieved via RAG from the shared `KnowledgeStore`.

No LLM call is made today. The `MockLLMProvider` generates investigation steps
deterministically from error pattern matching. The system is wired so a real LLM
(technical error → web lookup, business error → domain dictionary) can be plugged in
at a single point later with zero structural change.

```
POST /api/v1/incidents/triage
Content-Type: application/json
```

## Request Schema

```json
{
  "title":            "Spike in order rejections for corporate bonds",
  "description":      "40% of orders rejected with stale price error since 14:30 UTC. Market data feed showing 5s+ latency.",
  "affectedServices": ["order-gateway", "matching-engine", "market-data-feed"],
  "severity":         "HIGH"
}
```

**Validation rules:**
- `title` — required, non-empty string, max 200 chars.
- `description` — required, non-empty string, max 2000 chars.
- `affectedServices` — required, non-empty array of strings (each must match a known service name).
- `severity` — required, one of: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`.

## Priority Score Algorithm

The priority score is a **weighted composite** of four signals (max 100):

| Signal | Max pts | How computed |
|---|---|---|
| Severity | 30 | Fixed weight: CRITICAL=30, HIGH=22, MEDIUM=12, LOW=5 |
| Affected services | 25 | `min(affectedServices.length × 7, 25)` — capped at 25 |
| Similarity to past high-impact | 30 | Top retrieved incident score × 30 (0–1 → 0–30) |
| Time of day | 15 | Market hours (08:00–17:00 UTC) = 15, off-hours = 5 |

**Priority bands:**

| Score | Band | Meaning |
|---|---|---|
| 80–100 | P1 | Immediate response — trading impacted |
| 60–79  | P2 | Urgent — significant degradation |
| 40–59  | P3 | Standard — limited impact |
| 0–39   | P4 | Low — monitoring only |

```js
// services/triage/priorityScorer.js

const SEVERITY_WEIGHTS = { CRITICAL: 30, HIGH: 22, MEDIUM: 12, LOW: 5 };
const MARKET_HOURS     = { startHour: 8, endHour: 17 }; // UTC

/**
 * Computes a 0–100 priority score for an incoming incident.
 *
 * Each sub-score is isolated and testable independently.
 * The four signals are additive — no hidden multipliers.
 */
function computePriorityScore(incident, topSimilarityScore) {
  const severityScore         = scoreBySeverity(incident.severity);
  const affectedServicesScore = scoreByAffectedServices(incident.affectedServices);
  const similarityScore       = scoreBySimilarity(topSimilarityScore);
  const timeOfDayScore        = scoreByTimeOfDay(new Date());

  const total = severityScore + affectedServicesScore + similarityScore + timeOfDayScore;

  return {
    severityScore,
    affectedServicesScore,
    similarityScore,
    timeOfDayScore,
    total: Math.min(total, 100),
  };
}

function scoreBySeverity(severity) {
  return SEVERITY_WEIGHTS[severity] ?? 0;
}

function scoreByAffectedServices(services) {
  return Math.min(services.length * 7, 25);
}

function scoreBySimilarity(topScore) {
  // topScore is cosine similarity 0.0–1.0 from the KnowledgeStore
  return Math.round(topScore * 30);
}

function scoreByTimeOfDay(now) {
  const hour = now.getUTCHours();
  return (hour >= MARKET_HOURS.startHour && hour < MARKET_HOURS.endHour) ? 15 : 5;
}

function scoreToPriorityBand(total) {
  if (total >= 80) return 'P1';
  if (total >= 60) return 'P2';
  if (total >= 40) return 'P3';
  return 'P4';
}

export {
  computePriorityScore,
  scoreToPriorityBand,
  scoreBySeverity,
  scoreByAffectedServices,
  scoreBySimilarity,
  scoreByTimeOfDay,
};
```

## Investigation Steps — Pattern-Based Generation

Investigation steps are generated by matching the incident's title + description against
a library of **common web-application error patterns**. Each pattern defines:

- What keywords trigger it
- The ordered investigation actions
- Which logs / metrics to check
- The likely failure domain

This is the LLM plug-in point: today the `MockLLMProvider` runs the pattern matcher;
in future a real LLM replaces it, optionally augmenting with a live web search for
technical errors or a business-error dictionary for domain-specific errors.

## Pattern Matcher

```js
// services/triage/patternMatcher.js

import { ERROR_PATTERNS } from './errorPatterns.js';

/**
 * Matches an incident against the error pattern library.
 *
 * Strategy: score each pattern by how many of its keywords appear in the
 * incident text. Return patterns sorted by match score (highest first).
 * If no pattern scores > 0, return the 'unknown' fallback.
 *
 * This is intentionally simple — keyword frequency, not NLP.
 * An LLM replaces this function in a future integration.
 */
function matchErrorPatterns(incident) {
  const text = `${incident.title} ${incident.description}`.toLowerCase();

  const scored = ERROR_PATTERNS
    .filter(p => p.id !== 'unknown')
    .map(pattern => {
      const matchCount = pattern.keywords.filter(kw => text.includes(kw)).length;
      return { pattern, matchCount };
    })
    .filter(({ matchCount }) => matchCount > 0)
    .sort((a, b) => b.matchCount - a.matchCount);

  // Return matched patterns (up to 3), or the unknown fallback
  if (scored.length === 0) {
    return [ERROR_PATTERNS.find(p => p.id === 'unknown')];
  }

  return scored.slice(0, 3).map(({ pattern }) => pattern);
}

export { matchErrorPatterns };
```

## Investigation Steps Builder

Takes matched patterns and shapes them into the numbered step list returned in the response.
Steps from the top-matched pattern come first; steps from secondary patterns follow.

```js
// services/triage/investigationBuilder.js

import { matchErrorPatterns } from './patternMatcher.js';

/**
 * Builds the ordered investigation step list for a given incident.
 *
 * Steps from the primary pattern (highest keyword match) are listed first.
 * Secondary pattern steps are appended if they don't duplicate actions.
 *
 * Each step gets a sequential step number for easy reference during the call.
 */
function buildInvestigationSteps(incident) {
  const matchedPatterns = matchErrorPatterns(incident);
  const seenActions     = new Set();
  const steps           = [];
  let   stepNumber      = 1;

  for (const pattern of matchedPatterns) {
    for (const rawStep of pattern.steps) {
      // De-duplicate: skip if the same action already appears from a previous pattern
      if (seenActions.has(rawStep.action)) continue;

      seenActions.add(rawStep.action);
      steps.push({
        step:          stepNumber++,
        action:        rawStep.action,
        rationale:     rawStep.rationale,
        logsToCheck:   rawStep.logsToCheck,
        errorPattern:  pattern.id,
        failureDomain: pattern.failureDomain,
      });
    }
  }

  return steps;
}

export { buildInvestigationSteps };
```

## Mock LLM Provider for Triage

The `MockTriageLLMProvider` generates a triage summary using the pattern match results
and retrieved historical context. It is the sole LLM plug-in point for this capability.

**Future extension points (not built now):**
- **Technical errors**: LLM performs a web search for the matched error pattern
  (e.g., "matching-engine connection timeout root cause trading platform") and
  appends findings to the investigation steps.
- **Business errors**: LLM looks up the incident keywords against a business-error
  dictionary (loaded from config) and appends domain-specific resolution guidance.

```js
// services/llm/MockTriageLLMProvider.js

import { LLMProvider } from './interface.js';

/**
 * MockTriageLLMProvider — deterministic triage summary generator.
 *
 * Inputs:
 *   triageData   — { incident, scoreBreakdown, priorityBand, investigationSteps }
 *   context      — similar past incidents from RAG retriever
 *
 * Future LLM integration points are marked with TODO comments so they are
 * easy to find and hand off to a real provider.
 */
export class MockTriageLLMProvider extends LLMProvider {

  async analyze(triageData, context = []) {
    const { incident, scoreBreakdown, priorityBand, investigationSteps } = triageData;

    const topIncident    = context[0] ?? null;
    const startService   = this._identifyStartService(incident, investigationSteps);
    const failureDomains = [...new Set(investigationSteps.map(s => s.failureDomain))];

    // TODO (future — technical error): if investigationSteps[0].errorPattern is a known
    // technical pattern, call llmProvider.webSearch(pattern, incident.description) here
    // and append the findings as additional steps.

    // TODO (future — business error): if incident.description contains business-domain
    // keywords, load businessErrorDictionary.lookup(keywords) and append resolution guidance.

    return [
      `${priorityBand} incident — priority score ${scoreBreakdown.total}/100.`,
      topIncident
        ? `High similarity to past incident "${topIncident.incident.title}" (score ${topIncident.similarityScore}). Past resolution: ${topIncident.incident.resolution} (resolved in ${topIncident.incident.resolvedInMin} min).`
        : 'No closely matching historical incidents found.',
      `Start investigation at: ${startService}.`,
      `Likely failure domain(s): ${failureDomains.join(' → ')}.`,
      `${investigationSteps.length} investigation step(s) generated.`,
    ].join(' ');
  }

  /**
   * Heuristic: start at the service mentioned first in the top investigation step's
   * logsToCheck list, filtered against the incident's affected services.
   */
  _identifyStartService(incident, steps) {
    if (!steps.length) return incident.affectedServices[0] ?? 'unknown';

    const topStepLogs = steps[0].logsToCheck.join(' ').toLowerCase();

    const matchedService = incident.affectedServices.find(svc =>
      topStepLogs.includes(svc.toLowerCase())
    );

    return matchedService ?? incident.affectedServices[0];
  }
}
```

## RAG Retrieval (re-uses KnowledgeStore from Req 01)

The triage endpoint re-uses the same `KnowledgeStore` and `retriever.js` built in
Requirement 01. The query text is `incident.title + " " + incident.description`.

```js
// services/triage/index.js  — orchestrator

import { validateIncident }          from './validator.js';
import { retrieveRelevantIncidents } from '../rag/retriever.js';
import { computePriorityScore, scoreToPriorityBand } from './priorityScorer.js';
import { buildInvestigationSteps }   from './investigationBuilder.js';
import { getTriageLLMProvider }      from '../llm/index.js';

/**
 * triageIncident — main entry point.
 *
 * Readable step-by-step orchestration:
 *   1. Validate input
 *   2. Retrieve similar historical incidents (RAG)
 *   3. Compute priority score (similarity + severity + services + time)
 *   4. Generate investigation steps (pattern matching)
 *   5. Generate triage summary (mock LLM — real LLM plug-in point)
 *   6. Return structured response
 */
async function triageIncident(rawIncident) {
  // 1. Validate and normalise
  const incident = validateIncident(rawIncident);

  // 2. RAG — retrieve top similar historical incidents
  const query            = `${incident.title} ${incident.description}`;
  const similarIncidents = await retrieveRelevantIncidents(query);

  // 3. Priority score — top similarity score feeds into the composite formula
  const topSimilarityScore = similarIncidents[0]?.similarityScore ?? 0;
  const scoreBreakdown     = computePriorityScore(incident, topSimilarityScore);
  const priorityBand       = scoreToPriorityBand(scoreBreakdown.total);

  // 4. Investigation steps — pattern match against error library
  const investigationSteps = buildInvestigationSteps(incident);

  // 5. Mock LLM — generate augmented triage summary
  const llm     = getTriageLLMProvider();
  const summary = await llm.analyze(
    { incident, scoreBreakdown, priorityBand, investigationSteps },
    similarIncidents
  );

  return {
    incidentId:       `triage-${Date.now()}`,
    receivedAt:       new Date().toISOString(),
    priorityScore:    scoreBreakdown.total,
    priorityBand,
    scoreBreakdown,
    investigationSteps,
    similarIncidents: similarIncidents.map(({ incident: inc, similarityScore }) => ({
      id:             inc.id,
      title:          inc.title,
      similarityScore,
      severity:       inc.severity,
      rootCause:      inc.rootCause,
      resolution:     inc.resolution,
      resolvedInMin:  inc.resolvedInMin,
    })),
    summary,
  };
}

export { triageIncident };
```

## Future Integration Points (not in scope now)

### Technical Error → LLM Web Lookup

When the matched `errorPattern` is a known technical type (e.g., `database_error`,
`connection_timeout`), a real LLM provider will:

1. Receive the matched pattern ID and incident description.
2. Perform a targeted web search (e.g., via Perplexity or Tavily tool-call).
3. Append retrieved root-cause articles and recommended fixes as extra investigation steps.

Plug-in point: `MockTriageLLMProvider.analyze()` — replace the `TODO` comment block.

### Business Error → Domain Dictionary

When the incident description contains business-domain keywords (e.g., "margin call",
"settlement fail", "clearing rejection"), a business-error dictionary will:

1. Be loaded from a config file (`src/data/businessErrorDictionary.json`) at startup.
2. Provide structured root-cause definitions and regulatory/ops resolution steps.
3. Be injected as additional context alongside the RAG-retrieved incidents.

Plug-in point: same `MockTriageLLMProvider.analyze()` — second `TODO` comment block.

Neither of these changes requires modifying the orchestrator, the scorer, or the pattern
matcher — they are additive to the LLM layer only.

| Validation | O(1) | Field checks only |
| RAG retrieval | O(k) | k = knowledge store size; `MemoryVectorStore` is linear scan |
| Priority scoring | O(1) | Four arithmetic operations |
| Pattern matching | O(p × w) | p = patterns, w = keywords per pattern; both small constants |
| Step building | O(p × s) | p = matched patterns, s = steps per pattern; small constants |
| **Total** | **O(k)** | Dominated by the vector store scan — acceptable at seed-data scale |

**At scale:** Replace `MemoryVectorStore` with an ANN index (HNSW via Weaviate or
pgvector) to reduce retrieval from O(k) linear scan to O(log k).
